Auditoria completa do tracking Meta/Facebook Ads e UTMify
Escopo: checkout atual com Throne Elements e cartão de crédito.
Data da auditoria: 20/08/2026.
Alterações durante a auditoria: nenhuma. Esta resposta é somente análise.

Resumo executivo

Status: implementado, mas com dois conceitos diferentes.

Existem dois IDs:

anonymous_id do navegador:

gerado no localStorage;
usado inicialmente como identidade externa.
external_id do checkout:

derivado deterministicamente da chave de idempotência;

Após o checkout, o backend passa a usar o external_id derivado do checkout para o Meta CAPI.

Isso é correto para associar a conversão ao checkout, mas o external_id do navegador e o external_id do checkout não são o mesmo valor em todos os momentos da jornada.

Tabela de IDs

Meta
Para eventos que percorrem browser e CAPI:

browser usa eventID;
CAPI usa event_id;
nome do evento é o mesmo;
valor e moeda são os mesmos;
Purchase usa o mesmo ID determinístico.
Isso está correto para deduplicação do Meta.

Limitação da evidência
A maior parte dos testes atuais são testes de contrato por regex. Eles confirmam que o código contém a estrutura esperada, mas não simulam uma entrega real ao Meta.

O teste browser realizado confirmou:

request Meta PageView;
eid;
product_id;
billing_type;
ausência de Purchase em navegação passiva.
Não houve teste real de uma compra aprovada.

UTMify
A UTMify não recebe o event_id do Meta.

A API oficial de pedidos usa:

orderId

e não possui campo documentado:

eventId

O payload usa:

{
  "orderId": "<order_id>",
  "status": "paid",
  "products": [
    {
      "id": "hot-one-payment-off01",
      "planId": null,
      "planName": null,
      "quantity": 1,
      "priceInCents": "<valor>"
    }
  ]
}

A aplicação cria uma chave interna:

<transaction_id>:<event_type>

E calcula o ID do outbox como hash de:

destination + deliveryKey

Isso evita múltiplos registros locais para o mesmo evento lógico.

Risco
Não existe header de idempotência específico no envio para a UTMify.

Se o processo:

enviar o pedido;
receber resposta positiva;
cair antes de marcar o registro como entregue;
o retry poderá reenviar o mesmo pedido.

A aplicação evita duplicação localmente, mas a deduplicação final pela UTMify não foi comprovada por documentação ou teste operacional.

Portanto:

o tracking está separado como pagamento único;
a validação do webhook exige o produto canônico;

É necessário confirmar essa modalidade no produto/configuração da conta Throne.

Rota e assinatura

Arquivo:

Características:

Webhook antes do checkout
Status: implementado.

O sistema grava o evento como pendente/deferred e tenta reconciliar quando o checkout é criado.

Duplicidade
A entrega do webhook é identificada por hash do corpo bruto.

Isso significa:

o mesmo corpo exato é deduplicado;
o mesmo evento com serialização JSON diferente pode gerar outro hash;
o provider event_id não é uma chave única global.
Eventos fora de ordem
Existe ordenação por ranking e timestamp, mas a lógica de reconciliação e a lógica de processamento normal não são totalmente idênticas. Há risco em eventos com timestamps iguais ou estados terminais conflitantes.

10. Retries, fila e idempotência
Outbox
Existe uma fila persistente em banco para:

Meta;
UTMify.
Cada destino tem controle independente.

Retry
Características observadas:

timeout de aproximadamente 10 segundos;
primeiro retry após aproximadamente 15 segundos;
backoff exponencial;
limite de aproximadamente 6 horas;
máximo de 12 tentativas;
lease de processamento de 5 minutos;
reprocessamento de leases expirados;
worker inicial e polling periódico.
Problema encontrado
A função:

wakeConfiguredRetries()

aparenta ter a condição invertida.

Ela pode tentar acordar registros com erro meta_not_configured ou utmify_not_configured quando a integração está configurada, em vez de acordar quando a configuração foi corrigida.

Esse é um problema de prioridade alta porque pode deixar eventos parados mesmo depois que o secret é adicionado.

Dead letter
Não foi encontrado:

painel administrativo;
rota de reprocessamento;
dead-letter explícito;
mecanismo operacional para reabrir facilmente uma entrega failed.
Registros terminais permanecem no banco.

Pontos positivos
Tokens Meta, UTMify e Throne ficam no backend.
O Meta Pixel ID público não é secret.
Dados de cartão não são armazenados pelo aplicativo.
Não há CVV sendo processado pelo backend.
Webhook exige assinatura.
Purchase não pode ser criado pelo endpoint público /api/track-server.
E-mail, telefone e external ID são hashados antes do Meta CAPI.
Riscos
Não há rate limit visível para criação de checkout ou /api/track-server.
CORS não substitui autenticação.
O endpoint público aceita dados de atribuição e cliente controlados pelo navegador.
Isso pode gerar volume artificial de eventos/outbox.
Não há limites explícitos de tamanho de payload em todas as rotas.
Logs de erro do provider podem conter corpo de resposta sensível.
Webhook não possui janela de replay por timestamp/nonce.
O endpoint de auditoria usa comparação normal de token, não comparação constant-time.
Não há evidência de política de retenção para raw webhook e payloads de outbox.

Respostas objetivas
Meta Pixel e Meta CAPI usam o mesmo event_id?
Sim, para eventos que passam pelos dois canais. O Purchase usa purchase:<transaction_id> em ambos.

O UTMify Pixel recebe eventID explícito?
Não foi comprovado. O bootstrap oficial carrega o Pixel, mas o aplicativo não chama o Pixel UTMify com o eventID do Meta.

A API UTMify recebe um identificador estável?
Sim. Recebe orderId, e a aplicação também usa uma chave interna baseada em transaction_id + event_type.

A UTMify possui deduplicação própria comprovada?
Não comprovada. A aplicação tem deduplicação no outbox. A deduplicação final do provider não foi validada.

O Purchase só é disparado após confirmação server-side?
Sim, no desenho atual. O CAPI Purchase depende do webhook. O browser só dispara depois de status local pago e existência do Purchase no outbox Meta.

Pagamento único e assinatura estão separados?
No tracking, sim. No gateway, não está completamente comprovado. Não existe fluxo de assinatura, mas também não foi encontrado um campo explícito de cobrança única no payload Throne.

Renovações são diferenciadas da primeira conversão?
Não aplicável. Não existe assinatura ou renovação implementada.

Existe cenário de Purchase duplicado?
Sim, potencialmente:

retry após crash depois de resposta 2xx da Meta/UTMify;
callback browser repetido sem uma trava específica;
webhook semanticamente igual com serialização diferente;
provider externo sem idempotency key comprovada.
Existe cenário de perda de venda?
Sim, potencialmente:

integração configurada depois de uma falha not_configured;
erro terminal após o máximo de retries;
timeout na criação do checkout sem retry de aplicação;
ausência de operação para reprocessar registros failed.
O que precisa ser corrigido antes de considerar o tracking plenamente confiável?

Prioridade alta
Corrigir wakeConfiguredRetries().
Criar testes runtime para Meta, UTMify, webhooks e banco.
Confirmar no Throne que o produto está realmente configurado como cobrança única.
Adicionar idempotência ou reconciliação explícita no envio à UTMify.
Validar valores/moeda também no endpoint de status, não somente no webhook.
Garantir a persistência server-side de click IDs necessários ao Meta/UTMify.
Adicionar rate limit, limites de payload e proteção contra abuso.
Criar reprocessamento administrativo para eventos failed.
Reduzir/redigir corpos de erro de providers nos logs.
Prioridade média
Adicionar janela anti-replay ao webhook.
Criar unicidade baseada no provider_event_id.
Adicionar jitter nos retries.
Implementar testes browser de paridade de IDs.
Confirmar oficialmente se o Pixel UTMify suporta receber ou correlacionar um eventID customizado.
Adicionar métricas e alertas de filas, retries, falhas e idade de reconciliação.
Conclusão: a base está bem estruturada para Meta browser + Meta CAPI e o fluxo de Purchase está corretamente protegido contra criação pública. Porém, o sistema ainda deve ser classificado como parcialmente confiável em produção, principalmente por causa da ausência de confirmação do modo de cobrança no gateway, da paridade não comprovada com o UTMify Pixel, da falta de testes runtime e dos gaps de retry/deduplicação externa.
